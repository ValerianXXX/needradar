# Evidence Model

NeedRadar uses evidence levels to prevent a strong story from substituting for stronger proof.

| Level | Name | Minimum interpretation |
|---:|---|---|
| V0 | Hypothesis | An editorial idea with no qualifying public signal |
| V1 | Single signal | One accessible observation describes a plausible task |
| V2 | Repeated signal | Compatible observations recur across independent evidence |
| V3 | User confirmation | A relevant user provides structured confirmation |
| V4 | Completed action | A user completes a meaningful next action |
| V5 | Prototype delivered | A bounded prototype is available for real-task evaluation |
| V6 | Real-task use | Approved users attempt representative tasks |
| V7 | Repeat use | Relevant users return for additional tasks |
| V8 | Sustained outcome | Measured outcomes persist over an agreed period |

## Interpretation rules

- A source count is not a customer count.
- Multiple posts about one event may still be one underlying signal.
- A prototype is not evidence of adoption.
- Repeat use is not automatically evidence of business value.
- Revenue and ROI require their own records and attribution logic.
- Missing evidence stays missing; it is not filled with model confidence.

## Draft publication threshold

The representative policy implementation requires at least two accessible, PII-safe observations and either three independent author groups or two source policies. A complete draft must also identify the user, task, current workflow, desired outcome, AI path, human gates, counterevidence, and unknowns.

These thresholds are product policy, not universal market-research standards. A team should calibrate them against the decision risk and review the false-positive and false-negative rates.

## Counterevidence

Every opportunity must carry at least one reason not to invest. Common counterevidence includes mature incumbent tools, low task frequency, weak access to representative data, unacceptable error cost, and a workflow that does not need another abstraction layer.

## Unknowns

Unknowns are decision inputs, not writing defects. A useful unknown names the fact that would change the next decision: representative user access, baseline performance, integration constraints, evidence quality, switching cost, or the acceptable failure boundary.
